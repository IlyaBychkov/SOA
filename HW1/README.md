# Маркетплейс

Проект архитектуры маркетплейса, где продавцы размещают товары, а покупатели смотрят персональную ленту, оформляют заказы, оплачивают покупки, получают уведомления.

## Архитектура

Выбрал микросервисы: каждый сервис отвечает за свой домен. Веб-приложение обращается к ним через Nginx. Для обмена событиями используется Kafka. Оплата проходит через ЮKassa, письма отправляются через Яндекс Почту.

Сервисы планируются на Python с FastAPI, базы — PostgreSQL.

## Домены и сервисы

Каждому домену соответствует отдельный сервис:

| Домен / сервис | За что отвечает | Что хранит |
| --- | --- | --- |
| Пользователи | Аккаунты покупателей, продавцов, вход в систему | Аккаунты, роли, профили, контакты |
| Каталог | Добавление, редактирование товаров продавцами | Товары, продавцы товаров, категории, цены |
| Лента | Персональная выдача по истории просмотров | Просмотры, оценки интереса к категориям |
| Заказы | Оформление заказа, изменение его статуса | Заказы, покупатели, товары заказа, количество, цены на момент покупки, статусы |
| Платежи | Расчёт суммы заказа, проведение оплаты через ЮKassa | Суммы, валюты, номера платежей, связь с заказами, попытки оплаты, результаты |
| Уведомления | Отправка писем о статусах заказа, повторные попытки | Сообщения, получатели, статусы отправки, попытки доставки |

У каждого сервиса своя БД. Общих баз нет, напрямую к чужим таблицам сервисы не обращаются. Нужные данные получают через API или события Kafka.

## Почему такое разбиение

Аккаунт, роли, профиль находятся вместе в сервисе пользователей. 

Каталог отделён от заказов, потому что продавец может поменять цену товара, но в оформленном заказе должна остаться цена на момент покупки.

Лента отдельно хранит просмотры, определяет интересы покупателя. Карточки товаров она получает из каталога. Чем чаще покупатель смотрит товары какой-то категории, тем выше они будут в выдаче.

Платежи выделены отдельно, потому что у одного заказа может быть несколько попыток оплаты. Этот сервис работает с ЮKassa, а заказы по результату оплаты меняют свой статус. 

Уведомления тоже отдельно, потому что проблемы с отправкой письма не должны мешать работе с заказом.

## Рассмотренные варианты

### Модульный монолит

Одно приложение на FastAPI с модулями пользователей, каталога, ленты, заказов, платежей, уведомлений. Все модули запускаются вместе, используют одну PostgreSQL, но каждый работает со своими таблицами. Между модулями — обычные вызовы функций, Kafka для внутреннего обмена не нужна. ЮKassa, Яндекс Почта остаются внешними системами. Отправку писем можно выполнять в фоне внутри приложения.

### Микросервисы

Каждый из этих доменов находится в отдельном приложении со своей БД. Сервисы общаются через API, события Kafka.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Модульный монолит | Одно приложение проще запускать; внутренним вызовам не нужна сеть; связанные изменения данных можно сохранять одной транзакцией | Изменение одного модуля требует выпуска всего приложения; ленту нельзя масштабировать отдельно; сбой общего процесса затрагивает все модули |
| Микросервисы | Сервисы можно независимо обновлять; при росте просмотров можно отдельно масштабировать ленту; отправка писем работает в отдельном процессе | Нужно поддерживать несколько приложений, БД, Kafka; сетевые запросы могут завершаться ошибками; изменения статусов доходят через события с задержкой |

### Финальный выбор

Остановился на микросервисах. Персональная лента обрабатывает просмотры, каталог — изменения товаров, платежи — операции с ЮKassa, уведомления — отправку писем. У этих задач разные данные, зависимости. Отдельные сервисы позволяют менять, масштабировать их независимо, а сбой почтового сервиса не останавливает оформление заказа.

## Запуск

Нужны Docker, Docker Compose. Из папки `HW1`:

```bash
docker compose up --build -d
```

Проверить сервис каталога:

```bash
curl -i http://127.0.0.1:8000/health
```

Должен вернуться `200 OK` с ответом:

```json
{"status":"ok"}
```

Остановить:

```bash
docker compose down
```
